# 设计反思 3：可恢复性、部署与交付

## 审查结论

V3 已像运营工具，但仍假设网络稳定、管理员永不误连环境、请求结果总能即时返回。远程 PostgreSQL 与本地管理 EXE 的组合中，最危险的不是某个按钮缺失，而是“操作其实成功，客户端超时后又点了一次”或“以为在测试环境，实际修改生产”。

## 发现的问题

1. **环境身份不足**：只显示 API URL 不够，服务端必须返回环境名和唯一实例 ID。
2. **超时后的结果不确定**：客户端不能把超时直接当失败并允许无脑重试。
3. **首个 owner 流程未落地**：不能依赖迁移中的默认密码或手工 SQL。
4. **凭据保存策略需收紧**：首版不保存管理员密码；JWT 仅内存保存，关闭即退出。
5. **单文件 self-contained 并非必须**：会显著增大体积；本机已有 .NET 10，首版采用 framework-dependent x64 EXE，同时保留 self-contained 发布命令。
6. **升级兼容未定义**：客户端必须检查服务端 API 版本，不兼容时阻止写操作。
7. **审计与流水不是数据库备份**：内容变更和批量操作前仍需明确备份责任。
8. **范围过大影响首版质量**：若一次实现所有 V3 页面，测试深度会不足。
9. **测试缺少失败路径**：必须测试权限、并发、幂等、回滚、超时恢复，而不只测 200 响应。

## 最终修订原则

- 服务端公开管理握手信息：环境名、实例 ID、API 版本、迁移版本、服务器时间。
- 每个写请求客户端先生成幂等键；超时后可按键查询结果。
- 首个 owner 使用本地服务端 CLI 创建，密码仅命令执行时进入内存。
- 客户端不保存密码和 JWT，首版只保存非敏感 API URL。
- 生产环境首次连接和每次高风险操作显示醒目标识。
- 首版先把玩家处置闭环做深，再扩充内容编辑器；所有计划模块必须有明确“可用/只读/后续”状态。
- 交付包含迁移、管理员创建脚本、构建脚本、测试和使用文档。
