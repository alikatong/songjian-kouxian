# 设计反思 1：安全与领域一致性

## 审查结论

V1 功能面足够，但仍像“带权限的数据库编辑器”。修仙游戏数据存在强依赖：境界影响属性和可用装备，拍卖锁定资产，闭关影响灵气结算，邮件领取涉及幂等。允许管理员随意改字段会制造难以修复的角色状态。

## 发现的问题

1. **通用 PATCH 过宽**：同时修改境界、功法倍率和基础属性，可能重复计算或绕过突破历史。
2. **直接发资产与邮件发放重叠**：在线玩家读取背包时直接变更容易产生界面缓存和所有权竞态。
3. **撤拍语义不足**：只改拍品状态会丢失已扣库存，必须原子创建返还邮件。
4. **封禁不能真正踢下线**：现有玩家 JWT 七天有效；只写封禁字段不能阻止旧令牌继续调用 API。
5. **角色修复边界不清**：管理端不能复制一份战力公式，否则游戏更新后两套公式漂移。
6. **批量邮件缺少幂等键**：网络重试可能重复发放数千份附件。
7. **审计“前后快照”可能泄密或过大**：必须字段脱敏、限制大小，资产操作使用结构化差异。
8. **内容编辑立即生效风险高**：错误 JSON、负权重、断裂引用会影响全服。
9. **管理员 JWT 放内存不够**：需要 tokenVersion 每次校验和短时过期；敏感操作可要求重新输入密码。
10. **永久删除虽已禁止，但高风险资源扣除仍不可恢复**：需要逆向操作或补偿入口。

## 修订原则

- 从“字段编辑”改为“领域命令”：调节灵石、转移境界、结束闭关、修复属性、发放资产。
- 资产默认邮件发放；直接增减只用于纠错，且必须 reason、requestId、expectedVersion。
- 玩家和管理员都加入 `session_version`；认证中间件检查账号状态和令牌版本。
- 游戏公式只留在后端服务；管理端调用同一修复函数。
- 内容变更先校验再发布，保留发布版本和回滚快照。
- 所有批量写操作使用幂等键，返回任务状态。
- 高风险操作要求目标名称确认；批量操作要求输入目标数量确认。

## V2 必须改变

- 定义风险等级与确认方式。
- 定义角色版本控制和并发冲突。
- 定义批量任务状态机。
- 定义内容草稿、校验、发布、回滚生命周期。
- 将第一期范围压缩为可完整测试的核心能力，避免“每个页面只有半个功能”。
