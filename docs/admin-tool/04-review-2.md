# 设计反思 2：运营效率与可观测性

## 审查结论

V2 数据安全明显改善，但仍以数据实体组织界面。真实运营任务通常从问题开始，不会从“我要编辑 character 表”开始。若证据分散在多个页面，处理一次投诉需要反复搜索同一玩家，容易选错目标或漏写原因。

## 发现的问题

1. **缺少玩家时间线**：战斗、游历、邮件、拍卖、聊天、突破、管理员动作彼此隔离。
2. **资源变动没有业务流水**：审计只记录管理员写操作，无法解释灵石为何增加、附件何时领取。
3. **玩家详情缺少异常提示**：装备门槛、负逻辑状态、过期增益、卡住队列应自动检测。
4. **运营动作入口分散**：查看聊天违规后还要跳玩家页封禁，再跳邮件页补偿。
5. **内容编辑缺少影响范围**：修改某丹药前不知道商店、配方、邮件、玩家库存引用数量。
6. **无玩家视角预览**：公告、邮件正文和附件在管理端正确，不代表玩家端展示正确。
7. **缺少保存筛选与快捷动作**：玩家规模增长后，重复输入条件浪费时间。
8. **总览指标没有定义口径**：活跃、资产总量、成交量若口径不固定会误导平衡判断。

## 修订原则

- 围绕“事件时间线”和“处置工作台”组织玩家详情。
- 新建不可变资源流水，覆盖灵石、物品、装备的系统与管理员变化。
- 服务端提供角色健康检查，管理台只展示检查结果。
- 内容修改前返回引用计数、影响范围和校验结果。
- 高频动作保留在当前上下文侧栏，减少跨页。
- 邮件和公告提供玩家样式预览。
- 指标定义写进设计，避免前后端各自理解。
